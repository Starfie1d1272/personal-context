# 相关工作与复用策略

> **截至：** 2026-08-16  
> **状态：** 进行中的比较笔记  
>
> 这份文档记录当前讨论中已经形成的生态判断，用来约束项目不要把已有能力重新包装成“创新”。  
> 在对外做具体功能比较或版本级声明前，应再次核对上游仓库的最新实现。

---

## 1. 基本原则

现有生态已经覆盖了大量基础问题。

当前不能把以下单点当成 Personal Context 的独有创新：

- 长期记忆；
- 跨会话召回；
- 分层上下文；
- 混合检索；
- 嵌入 / 重排序模型；
- 时态事实；
- 来源追溯；
- ACL / 权限；
- Agent 装配；
- 经验 → Skill；
- 上下文注入；
- 记忆查看器；
- 多 Agent 共享某种记忆。

Personal Context 的研究问题必须建立在这些已有能力之上。

---

## 2. DeepSeek Harness (DSH)

### 已解决 / 可复用

- Agent 运行时；
- 插件 / 能力接缝；
- 会话；
- 模型 / 工具抽象；
- Skills；
- 存储；
- 权限 / 审批；
- 沙箱；
- 工作流 / 任务；
- 客户端界面扩展；
- Profile / Bundle / 预设；
- 外部协议 / 子 Agent。

### 对本项目的意义

DSH 非常适合作为第一运行时和自用验证环境。

尤其重要：

- 会话日志可以成为证据账本；
- pre-step 是上下文组装的实现落点；
- 存储-领域可以承载第一版结构化数据；
- Profile / Bundle 可以承载 Personal DSH Distribution。

### 不是我们的创新

- “一切皆插件”；
- 可插拔 Agent 框架；
- 在模型调用前注入上下文；
- Agent 权限 / 沙箱。

---

## 3. GenericAgent (GA)

### 已解决 / 启发

GA 的重要思想包括：

- 上下文信息密度；
- 极小长期索引；
- 分层记忆；
- 经验 → SOP / 代码 / Skill；
- 自我进化；
- 强调让有限上下文中保留最具决策价值的信息。

### 真实使用中暴露的缺口

GA 的极小文本索引依赖：

```text
LLM 看懂 hint
→ 意识到深层内容存在
→ 主动 file_read
→ 正确理解
→ 在决策中正确使用
```

强模型下很优雅，但可靠性仍依赖模型：

- 可能没意识到应该读；
- 可能读到了却没有正确使用；
- Markdown 被迫承担部分检索策略 / 语义；
- 文本事实库不适合作为当前权威状态。

### 对本项目的取舍

保留：

- 信息密度；
- 经验 / Skill 演化；
- Markdown 作为 SOP / Skill / 经验片段内容载体。

替换或降权：

- LLM 维护的权威文本事实；
- 让 Markdown 承担数据库 / ACL / 状态机；
- 让主模型成为长期事实检索控制器。

---

## 4. MemOS

### 已解决 / 可复用

当前讨论中将 MemOS 视为成熟的：

- 长期记忆；
- 召回 / 捕获；
- 经验 / 策略 / 世界模型式学习；
- Skill 演化；
- DSH 集成；
- 查看器 / 管理界面。

### 对本项目的意义

MemOS 是：

- 重要参考实现；
- 记忆 / 学习提供方候选；
- 主要基线。

### 不能再宣传为差异化

- “用户能看到记忆”；
- “不同 Agent 共享长期记忆”；
- “经验变成 Skill”；
- “DSH 有长期记忆”。

### 仍需上层治理的问题

MemOS 或其它记忆提供方的派生认识进入 Personal Context 时，不能因为被模型抽取出来就自动成为权威状态。

默认应进入：

```text
证据 / 候选 / 修改建议
```

再由 Personal Context 决定是否沉淀。

---

## 5. OpenViking

### 已解决 / 可复用

讨论中将 OpenViking 视为重要上下文数据库 / 检索基线：

- 资源 / 记忆 / Skill；
- 分层组织；
- L0 / L1 / L2；
- 语义 / 分层检索；
- 重排序；
- 会话抽取；
- 检索追踪。

### 对本项目的约束

以下不能单独声称创新：

- 分层上下文；
- “只取相关信息”；
- 分层检索；
- 上下文数据库本身。

### 可能的角色

- 检索提供方；
- 上下文基线；
- 下层内容 / 记忆提供方。

---

## 6. Graphiti

### 已解决 / 可复用

Graphiti 已经证明以下问题有成熟实现：

- 时态事实；
- 有效 / 无效时间；
- 来源追溯 / 经验片段关联；
- 图关系；
- 当前与历史事实；
- 混合检索。

### 对本项目的约束

不能把：

```text
valid_from
invalid_at
来源追溯
时态事实图
```

本身宣传成创新。

### 仍然不同的问题

Personal Context 更关心：

- 当前权威状态如何进入最终 Agent 上下文；
- 主张与状态的不同冲突语义；
- 最终披露 / 组装；
- 用户治理。

Graphiti 可以成为状态 / 时态提供方，而不是被重写。

---

## 7. TencentDB Agent Memory

### 已解决 / 可复用

讨论中关注其：

- 聊天记忆 / Skill / Wiki / CodeGraph；
- 责任方 / ACL；
- Agent 装配；
- 版本 / 状态；
- BM25 + 向量 + 融合。

### 对本项目的约束

不能把以下单点当成创新：

- 记忆有 ACL；
- 不同 Agent 看到不同知识；
- 权限过滤后再检索；
- 混合检索。

### 仍值得研究

Personal Context 进一步关心：

- 字段 / 记录级披露；
- 目标模型 / 提供方特定披露；
- 脱敏；
- 最终上下文责任；
- 完整上下文编译记录审计。

## 8. PowerContext / Mnemon / dsh-native-memory / dsh-memory-evolve

这些项目在此前讨论中主要作为 DSH 生态参考。

### PowerContext

值得关注：

- 持久上下文；
- 经验 / Skill；
- DSH 适配器；
- 上下文提供方角色。

适合作为提供方候选，而不是权威个人状态。

### Mnemon

值得关注：

- 运行时记忆；
- 文档；
- 记忆空间；
- 受监督写入；
- 界面；
- 跨 Agent 共享。

与 Personal Context 接近，但重点仍然偏记忆。

### dsh-native-memory

设计上值得参考：

- DSH 存储域；
- 会话查询；
- 审批门控写入；
- 来源追溯；
- 密钥检测；

### dsh-memory-evolve

覆盖面很广，包含记忆 / Skill / 待办 / 项目日志 / 多会话 / 外部 AI 等。

当前更适合作为设计参考，而不是核心依赖，避免形成两个编排责任方。

## 9. 当前真正的差异化假设

经过排除后，项目可能有价值的不是一个新算法，而是以下组合：

```text
模式支撑长期控制面
+
状态 / 主张 / Skill 决策语义
+
证据 → 修改建议 → 治理 → 写入
+
时效性 / 过期 / 重新验证
+
类型感知上下文组装
+
确定性披露
+
单一最终组装责任方
+
多提供方接入
+
用户可见治理
```

目前应称为：

> **架构假设 / 设计论点**

而不是首创声明。

---

## 10. 当前宣传上应避免的误区

不应把以下作为头部差异化：

### “你的上下文属于你”

这是重要愿景，但用户自主、本地 / 自托管、可导出等概念并非空白市场。

### “多个 AI 共享同一份记忆”

MemOS 等已有系统已经覆盖相当多。

### “用户可以查看 AI 记住了什么”

记忆查看器并不独有。

### “只给 Agent 相关上下文”

GA、OpenViking、MemOS、成熟 RAG 系统都已经深入研究。

### “时间状态 / 来源追溯”

Graphiti 等已经构成强对照。

更有辨识度的产品主张应围绕：

- 记忆会维护和过期，而不是只增长；
- 结构化长期状态而非模型维护 Markdown；
- Agent 不只是“搜到”，而是得到正确的上下文 / 能力；
- 用户能看到当前世界模型、过时条目、修改建议和上下文编译记录；
- 系统能否把强模型一次探索沉淀成以后更便宜模型可稳定复用的能力。

---

## 11. 优先复用

第一阶段应优先复用：

| 能力 | 首选策略 |
|---|---|
| Agent 运行时 | DSH |
| 会话 / 证据日志 | DSH |
| 记忆 / 学习 | MemOS / 其他提供方 |
| 分层上下文 | OpenViking 或类似方案 |
| 时态图 | Graphiti 或类似方案 |
| 检索 | 现有全文检索 / 向量 / 重排序模型 |
| Skill 运行时 | DSH / 现有生态 |
| 领域应用 | 在现实可行处使用适配器 |

本项目最不应该做的事情之一，就是为了看起来“原创”而重写成熟基础设施。
