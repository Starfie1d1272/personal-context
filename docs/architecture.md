# 架构与集成

> 更新：2026-10-17。本文描述设计及渐进探索路径；原则见[当前设计状态](design-state.md)，上游实现证据见[相关工作](related-work.md)。

## 1. 逻辑职责与组件

| 职责 | 输入与输出 | 可能的承载方式 |
| --- | --- | --- |
| 信息输入 | 个人录入、文件、工具结果与现实变化 → 原始依据 | 专业应用、插件、文件引用、事件 |
| 长期记录 | 依据 → 实体、观察、状态、主张、经验与关系 | 现有记忆组件、结构化领域记录、内容文件 |
| 更新与纠错 | 新依据或反馈 → 修订、冲突、待处理建议 | 确定性规则、现有管线、必要的模型辅助 |
| 按需准备 | 当前活动与授权 → 所需上下文和能力 | 查询、检索、范围过滤、组装规则 |
| Agent 工作环境 | 上下文、工具、Skills 与权限 → 工作结果 | DSH 及其插件、配置组合 |
| 人用界面 | 当前信息与历史 → 查看、编辑、纠正 | 专业应用、已有 Viewer、必要的界面扩展 |
| 迁移与反馈 | 长期资产和使用记录 → 导出、规则改进 | 稳定引用、修订记录、适配与导出接口 |

每行表示职责，具体实现可以合并或复用已有组件。先检查正式接口是否满足领域需求，再决定是否增加存储或服务。直接修改上游内部数据库会增加升级与迁移负担，应优先使用正式扩展机制。

Git、文献与记账应用可以继续维护原始业务记录。系统保存稳定引用、必要的本地副本和跨域关系，并标明哪个来源负责哪个字段；来源不可访问时标记状态和最近核对时间。没有接口的应用可以先采用显式导入或手工录入。

## 2. 共同骨架与领域结构

采用**少量共同元数据＋领域字段＋原始材料引用**。以下是候选设计，不是已经实现的 schema。

| 维度 | 要表达的内容 |
| --- | --- |
| 身份与对象 | 记录标识、描述的实体、外部对象对应关系 |
| 内容与原件 | 值或正文、文件版本、页码、表格或工具结果位置 |
| 来源与归属 | 谁记录、谁提出、谁采纳、模型是否进行了推断 |
| 时间 | 观察或事件时间、实际有效时间、系统记录时间 |
| 范围与授权 | 适用活动、项目、对象或环境；另行表示接收方与处理权限 |
| 性质与状态 | 观察、引用、计划、推断等；当前、历史、待确认、撤回等 |
| 关联与修订 | 支持、反对、限定、替代、纠正，以及派生内容依赖的版本 |

字段按需要使用。未知时间和缺失值保持未知；单个置信度分数无法替代来源、条件和冲突。记录之间可共享证据，同一来源被重复转述不能累加为独立证据。

观察记录某时发生或测得的内容；状态表示目前对对象的理解，可由事件和观察形成；主张保存提出者及依据；Skill 保存方法、前提和预期结果。实体、原始数据、文件也有自己的结构。它们可以互相关联，类型不必穷尽且互斥，也不要求分别存入不同数据库。

PDF、照片、实验数据和长文保留原始形式。Skill 正文可以是 Markdown 或代码，其元数据记录环境、版本、所需工具、成功与失败依据。一次成功只支持相应条件下的结果，推广范围需要后续证据。

## 3. 三组贯穿例子

以下全部为合成场景，日期与标识仅用于解释行为。

### 眼镜与验光

| 记录 | 含义 | 更新方式 |
| --- | --- | --- |
| `measurement-A` | 6 月某次测量，附左右眼、单位、测量条件及单据引用 | 保存历史观察；发现转录错误时建立纠正关系 |
| `glasses-A` | 当前佩戴的一副眼镜，镜片参数有独立依据 | 根据实际配镜或更换记录更新 |
| `measurement-B` | 10 月新增测量 | 追加观察，不直接改变当前镜片参数 |
| 用户描述 | 对佩戴体验的自述 | 保留说话者、时间和原话含义 |

询问“当前眼镜参数”时查镜片记录；回顾测量变化时查两次观察。若当前镜片来源缺失，返回未知，不能用最近测量补成确定值。用户纠正一次识别错误后，后续重新导入同一单据需要沿用纠正或提出冲突。

这里讨论记录语义，不提供验光判断或配镜建议。

### 衣服、家电与设备

一件设备 `device-A` 有型号、具体实物身份、购买事件、位置及拥有状态。型号规格、当前配置和实测结果分别关联，避免把产品介绍当成实物状态。

1. 8 月购买，订单作为依据；当前拥有状态据此建立。
2. 9 月转赠，追加事件并更新拥有状态，购买历史保留。
3. 10 月补录旧订单，系统记录时间变新，事件时间仍为 8 月，不能恢复为当前拥有。
4. 配置现有工作环境时，排除已转赠设备；查询过去购买情况时，返回历史。
5. 若另一台同型号设备被误合并，用户修正实体对应，关联状态与后续检索随之调整。

衣服同样可以记录购买、退货、转赠和评价。“计划购买”保持意向状态；长时间未提及不能自动判定闲置。现实发生转赠和发现原订单从未成交，应分别记为变化与纠正。

### 论文与知识

论文 `paper-A` 关联一个固定版本。某张表格记录特定样品、方法、条件、单位和误差；作者据此提出解释 `claim-A`，用户添加评注 `note-A`。原始数据和处理后的数据保留各自来源。

阅读时，系统按问题提供可定位的观察、作者解释和用户评注。另一篇论文提出不同解释时，先核对实验条件，再建立支持、限定或冲突关系。两种观点可以并存，相关反证应进入讨论。

新论文出现不自动替代旧主张；用户尚未表达接受，也不能写成用户已采纳。只打开文件只能证明一次访问。若原文发布更正，依赖旧表格的摘要和认识标记为待复查，后续使用同时交代更正。

## 4. 按需读取

一次活动首先确定对象、项目、时间需求、接收方和允许的处理范围。

1. 在允许范围内，对已知对象和字段进行直接查询。
2. 对资料和经验使用全文、向量或已有记忆组件生成候选。
3. 核对对象、适用条件、修订状态和时效，去除重复；历史问题按相应时间取值。
4. 必要时重排或摘要，保留重要来源、限定及分歧。
5. 在预算内输出所需信息，并准备适用的工具和 Skills。没有合适证据时返回空结果、未知或待确认。

访问限制在候选获取时生效。向外部嵌入、检索、重排或摘要服务发送内容前，按该服务重新核对允许范围；最终提供给 Agent 前再检查一次。数据库在本地并不能说明模型加工也在本地，配置和界面需要表达真实流向。

数据库查询、检索、程序规则和模型可共同承担读取。本地模型的实际效果仍取决于资料和任务，复杂归属、意向和条件判断需要保留不确定性。

一次组装应能追查：活动及接收方、候选来源、采用或排除理由、使用的记录版本、最终披露内容和预算。审计记录本身也受权限与保留规则约束，避免额外复制敏感正文。

## 5. 更新、纠错与遗忘

输入可以来自对话，也可以来自购买、处置、文献导入、工具结果或用户编辑。系统保存依据，校验对象与字段，再按来源和操作性质更新。

| 变化 | 处理倾向 |
| --- | --- |
| 用户明确编辑自己的记录或偏好 | 保存修订与依据，更新相应视图 |
| 来源明确的系统事件或工具结果 | 按预先定义的规则入库，保留对象与时间 |
| 模型从多条对话推断偏好 | 带来源的候选，避免直接覆盖已确认状态 |
| 关键状态冲突 | 保留旧值及新证据，提示具体待判断部分 |
| 新的支持或反证 | 更新证据关系与适用条件，保留认识归属 |
| 来源更正、撤回或删除 | 追踪依赖，更新或移除派生摘要、索引与推断 |

用户纠正要记录对象、范围和当前效力。旧记录重放、重复导入、后台归纳不能无条件恢复已纠正内容；新的相关证据可以提出变更。来自模型的转述仍沿用原始证据链。

过时表示需要重新核对，不能仅按时间把所有内容判错。事实有效时间和入库时间分开；用户询问历史时应能返回当时记录及后续纠正。删除和撤回还需说明对缓存、导出副本及外部服务的实际控制范围。

规则清楚的低影响更新可以自动处理；推断、冲突和高影响修改采用适合场景的确认方式。具体分级保持开放。

## 6. 使用反馈怎样改变系统

| 反馈 | 优先修正的位置 |
| --- | --- |
| 内容错误 | 原始解释、记录与修订关系 |
| 内容已过时 | 有效时间、替代状态和派生索引 |
| 内容正确但用错活动 | 适用范围与选择规则 |
| 同话题但对象错误 | 实体映射、项目或工作空间 |
| 超出授权范围 | 访问与披露配置、组件注入路径 |
| 方法导致失败 | Skill 前提、步骤和预期结果 |

反馈同时连接“维护什么认识”和“怎样使用认识”。用户可以从日常页面查看当前信息，需要时展开一次使用的来源与过程，再完成具体修正。

## 7. DSH 组合探索

DSH 承担 Agent 工作环境，已有插件承担记忆与经验。具体已存在能力、默认配置和版本限制集中列在[相关工作](related-work.md)。在固定快照中，MemOS 有原生 DSH bundle，但其声明版本范围与所引用的 DSH 版本不匹配，组合尚未安装运行验证。

建议按如下顺序推进：

1. **确定兼容组合。** 核对运行时、插件和模型配置，选择有依据的版本组合或完成适配，记录实际数据流向。
2. **体验现成能力。** 使用隔离的合成数据走通捕获、检索、查看和纠正，了解后台处理与下一次读取的时序。
3. **跑通一个完整流程。** 记录设备、查询当前状态、更新转赠、按活动使用、纠正一次不合适的引用。
4. **补具体缺口。** 根据实际接口增加领域记录、修正操作、范围规则或界面入口；验证是否能持续生效。
5. **记录发现。** 说明哪些靠配置完成、哪些需要代码、哪些设计应调整，再扩展到论文或项目。

开始实现后，检查跨重启保存、修正后再使用、旧数据补录、范围限制以及插件失败时的基本交互。产物可以是集成说明、可运行配置、合成例子和小型适配代码。实现前不创建空目录或虚构安装步骤。

跨 Agent 接入应保留来源、时间、关系、修订与权限。是否采用 MCP、如何同步多设备、是否形成整合包，继续在[开放问题](open-questions.md)中讨论。
