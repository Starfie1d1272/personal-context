# Personal Context

> **让长期 AI 协作不只是“记得更多”，而是能够长期维护一份可靠、可追溯、可治理、按需使用的上下文。**

Personal Context 是一个面向长期 AI / Agent 协作的早期研究与系统设计项目。

它关注的不是如何再做一个 Memory、RAG 或 Agent Runtime，而是一个更长期的问题：

> **当 Agent 持续使用关于用户、项目和现实环境的信息时，这些信息应该如何保持正确、知道依据、处理变化，并在每一次任务中被正确地交给 Agent？**

项目目前处于设计与验证阶段。这里记录的是一套需要被实验验证的架构假设，而不是一个已经完成的产品。

---

## 现有系统解决了什么，还缺什么？

这个项目大量借鉴并计划复用现有 Agent 和 Memory 基础设施，而不是从头重做它们。

其中最重要的三个参考是 **[DeepSeek Harness（DSH）](https://github.com/deepseek-ai/deepseek-harness)、[GenericAgent（GA）](https://github.com/lsdefine/GenericAgent) 和 [MemOS](https://github.com/MemTensor/MemOS)**。

### DSH：运行时已经有了，但长期认知仍然需要内容和语义

DSH 提供了很好的 Agent 运行基础设施：

- Agent 生命周期；
- 会话与工具；
- 插件系统；
- Skills；
- 存储；
- 权限与审批；
- 沙箱；
- Profile / Bundle / Preset；
- UI 和外部集成。

它解决的是：

> **Agent 怎样运行和组合能力？**

但运行时本身并不会回答：

- 关于用户和环境的长期信息应该怎样组织；
- 哪个状态现在仍然有效；
- 一条信息依据什么成立；
- 什么变化可以自动写入；
- 什么应该过期或重新验证；
- 这一次到底应该把哪些长期信息交给 Agent。

因此 Personal Context 把 DSH 看作**第一运行时和组合底层**，而不是长期数据语义本身。

---

### GenericAgent：经验和 Skill 很有价值，但不能把可靠性全部交给模型

GA 的两个核心思想对本项目非常重要：

- 提高上下文的信息密度；
- 从真实任务经验中形成可复用的 SOP / Skill。

但如果长期信息主要存在于 Markdown 中，再依赖模型完成：

```text
看到索引
→ 意识到某条信息可能有用
→ 主动读取对应文件
→ 正确理解
→ 正确应用
→ 必要时正确修改
```

这使系统可靠性明显依赖模型本身的能力；在较弱或较便宜的模型上，这些风险是否进一步放大，也是 Personal Context 希望验证的问题。

这些风险包括：

* 忽略本应读取的信息；
* 召回错误或不完整的内容；
* 把过时信息继续当成当前事实；
* 在总结和改写过程中产生偏差；
* 让长期文本在反复生成和更新中逐渐漂移。

Personal Context 希望把其中一部分责任从“模型自己记得做对”，下沉到**结构化数据、明确工具和运行时控制面**。

---

### MemOS：Memory 很强，但 Memory 不等于长期世界状态

MemOS 已经覆盖了很多本项目不应该重复实现的能力：

* 长期 Memory；
* 会话和轨迹记录；
* 经验组织；
* 记忆召回；
* 学习与演化；
* Skill / policy 类能力形成。

因此 Personal Context 并不试图再造一个 Memory OS。

真正剩下的问题是：

> **被记住的信息，应该以什么语义影响未来 Agent？**

例如：

```text
“这个项目现在使用 pnpm。”
“过去几次任务似乎都使用了 pnpm。”
“以后处理这个项目时优先使用 pnpm。”
```

它们都可以进入 Memory，但其实分别更接近：

* 当前状态；
* 从经验中得到的判断；
* 可复用的行为规则。

如果把它们都当作统一的“记忆项”，后续的冲突、失效、验证和使用方式就很难保持清晰。

Personal Context 因此把 MemOS 看作重要的**记忆 / 学习提供方与基线**，而在其上增加长期认知的语义、治理和最终上下文控制。

---

## Personal Context 增加了什么？

Personal Context 当前的核心假设是：

> **长期 Agent 需要的不只是 Memory，而是一层结构化的长期认知控制面。**

这层控制面至少区分三类长期资产。

### 状态：现在是什么？

例如：

```text
当前操作系统
当前项目分支
当前包管理器
当前项目阶段
某个设备现在的状态
```

状态重点关注：

* 当前有效性；
* 来源权威性；
* 更新时间；
* 生命周期；
* 被取代和重新验证。

---

### 主张：我们有什么理由相信什么？

例如：

```text
论文 A 支持解释 X
论文 B 对解释 X 提出了限制
目前证据不足以确定 X
```

主张允许：

* 多个观点同时存在；
* 支持与反对；
* 不同适用范围；
* 不确定性；
* 不同证据强度。

新的主张不一定覆盖旧主张。

---

### Skill：这种情况下应该怎么做？

例如：

```text
处理项目依赖升级前先检查 lockfile
遇到某类网络故障时先检查节点健康
```

Skill 关注：

* 前置条件；
* 适用环境；
* 执行步骤；
* 验证标准；
* 可靠性；
* 成功和失败历史。

---

## 证据不等于事实

状态、主张和 Skill 都应该能够追溯到证据。

证据可以来自：

```text
用户输入
DSH 会话
工具结果
Git
文件
系统探针
论文
网页
数据集
外部应用
完整任务轨迹
```

但：

> **观察到一件事，不等于系统已经有资格把它写成长期事实。**

因此默认写入路径是：

```text
观察 / 对话 / 工具结果
        ↓
       证据
        ↓
    候选解释
        ↓
     修改建议
        ↓
权威性 / 冲突 / 风险
        ↓
       治理
        ↓
       写入
```

LLM 可以提出：

> “世界可能发生了变化。”

但它不天然拥有直接修改长期权威状态的权限。

---

## 从“记忆召回”到“上下文编译”

Personal Context 的另一项核心假设是：

> **Agent 最终需要的不是搜索结果，而是为当前活动准备好的运行上下文。**

因此读取路径不是简单的：

```text
搜索
→ 找几条最相似的 Memory
→ 塞进 prompt
```

而更接近：

```text
当前活动
   ↓
范围与硬性约束
   ↓
候选检索
   ↓
融合 / 重排序
   ↓
状态 / 主张 / Skill 分别处理
   ↓
时效性 / 权威性
   ↓
token 预算
   ↓
权限与披露
   ↓
上下文编译
   ↓
Agent
```

检索仍然可以复用 BM25、向量检索、图检索、MemOS、OpenViking、Graphiti 等成熟系统。

Personal Context 重点负责的是：

> **这些候选最终应该怎样影响这一次 Agent。**

---

## 当前真正想验证的创新点

Personal Context 不把下面这些单独宣传为创新：

* 长期 Memory；
* RAG；
* 向量检索；
* 分层上下文；
* 时间事实；
* Agent 共享 Memory；
* Experience → Skill；
* Memory Viewer；
* Agent 插件系统。

这些领域已经有大量优秀工作。

当前真正需要验证的是下面这组组合是否具有独立价值：

```text
结构化长期控制面
+
状态 / 主张 / Skill 的不同决策语义
+
基于证据的写入治理
+
生命周期 / 过期 / 重新验证
+
类型感知的上下文编译
+
确定性的权限与披露
+
多提供方接入
+
用户可见、可修改、可审计
```

这目前是一项**架构假设和研究论点**，而不是“世界首创”的声明。

---

## 为什么这可能有价值？

如果这个方向成立，长期 Agent 应该不再只是：

> **“拥有越来越多 Memory。”**

而是逐渐具备下面这些能力。

### 记忆会被维护，而不只是增长

系统应该知道：

* 什么仍然有效；
* 什么已经过时；
* 什么需要重新确认；
* 什么已经被新状态取代。

---

### 用户可以看到 AI 的长期认识

用户应该能够直接回答：

> **你为什么知道这件事？**

以及：

> **为什么这一次 Agent 可以看到它？**

长期认知不应该重新变成一个不可见的 Memory 黑箱。

---

### 系统承担更多责任，而不是无限依赖模型能力

如果环境、状态、适用 Skill 和权限能够由运行时提前准备，那么 Agent 不必每次都依赖模型自己：

```text
发现
→ 理解
→ 回忆
→ 判断
→ 重新探索
```

这可能尤其有利于较弱、较便宜的模型。

一个重要实验问题是：

> **强模型第一次完成一个任务并沉淀经验以后，第二次能否让明显更弱、更便宜的模型，以更少 token、更少工具调用稳定完成？**

如果可以，说明部分“智能”已经真正沉淀到了系统，而不仅仅存在于一次模型调用中。

---

## 当前架构

```text
                 证据来源
                    │
        用户 / DSH / 工具 / Git / 文件
                    │
                    ▼
                   证据
                    │
                    ▼
             候选解释 / 修改建议
                    │
                    ▼
                   治理
                    │
                    ▼
        ┌──────────────────────┐
        │ Personal Context     │
        │                      │
        │ 状态                 │
        │ 主张                 │
        │ Skill                │
        │ 证据引用             │
        │ 生命周期             │
        │ 权限 / 披露          │
        └──────────┬───────────┘
                   │
                   ▼
              上下文编译
                   │
                   ▼
                  Agent
```

第一阶段计划以 **DSH** 作为运行时，并尽量复用已有的 Memory、检索、Skill 和 Agent 基础设施。

---

## 当前阶段

Personal Context 目前仍处于**设计与早期验证阶段**。

第一个原型计划从一个很小但可验证的场景开始：

> **设备与项目运行环境**

例如让系统长期维护：

```text
设备
操作系统
项目
当前分支
包管理器
运行时
依赖环境
```

然后完整验证：

```text
状态
→ 上下文编译
→ Agent 行动
→ 新证据
→ 修改建议
→ 治理
→ 状态更新
```

项目并不预设这一独立层一定必要。

如果最终发现：

> **DSH + MemOS / OpenViking / 其它成熟系统 + 很薄的适配层**

已经可以用更低复杂度得到相同结果，那么合理的结论就是缩小 Personal Context，而不是为了维护项目本身继续增加架构。
